A route for the work ahead.

What is the main unknown? Choose a route when the task needs discovery, proof, or coordination.

Survey

Clarify the few product, design, architecture, or quality-bar unknowns that could change the implementation route.

Use whenUser intent is unresolved and the alternatives materially change the result.
Exit withA supported target and an explicit definition of success.

Track

Follow evidence from symptom to owning seam. A failing test, log, or report begins the investigation; it does not get to dictate the fix.

Use whenBehavior is failing, flaky, slow, regressed, or inconsistent.
Exit withA supported root cause and the smallest responsible repair.

Prove

Define one expected behavior with a focused failing test, then make the smallest change that turns that evidence green.

Use whenA test-first proof is requested for a narrow behavior.
Exit withA passing proof plus owned-diff review and validation.

Expedition

Coordinate complex implementation across coupled contracts, dependencies, or multiple owners. Keep the plan proportional and carry the work through validation and review.

Use whenThe route is clear, but implementation needs substantial coordination.
Exit withA verified result, explicit risks, and authorized delivery state.

A straightforward change? Inspect, implement, verify, and review. The entrypoint is enough; no formal mode or planning document is required.

Good work starts with a useful brief.

Say what you know, where your experience ends, and what would change your mind. The guide can help uncover the rest.

Find my blind spots
“Do a blind-spot pass. Explain the few unknown unknowns that could change the route, and help me prompt you more precisely.”
Let me react first
“Before touching production code, prototype three cheap, meaningfully different directions with fake data.”
Ask what matters
“Interview me one question at a time. Prioritize answers that would change the architecture, contract, UX, or definition of success.”
Make the plan reviewable
“Lead with the decisions I am most likely to revise. Put mechanical edits after the data, interface, rollout, and visible-behavior choices.”
Leave room for the territory.

Real constraints deserve precision. But an over-specified implementation can keep an agent on the wrong route after the repository supplies better evidence; a vague request invites assumptions that may not fit. Describe the outcome and constraints, then let verified evidence revise the map.

The plan meets the code.

A useful plan can adapt without turning every implementation choice into a meeting.

Incoming request
“Add a safer workspace deletion flow. I know the right confirmation when I see it, but I’m unfamiliar with this part of the app.”
01Survey the unknowns

Inspect the current flow and prototype three cheap confirmation patterns. The user selects typed confirmation.

02Set a focused route

Reuse the existing dialog, preserve the API, and define focused behavior and accessibility checks.

03Meet new evidence

The API reveals a 30-day recovery window, making the planned “permanent” warning inaccurate.

04Revise the map

Correct the warning to describe the existing recovery window and continue. Ask only if the actual deletion behavior needs to change.

05Report the territory

Lead with the safer flow, then disclose the owned delta, tests, deviation, remaining risk, and delivery state.

Three operating promises.

The deeper policies exist to uphold these outcomes—not to add ceremony to every task.

01

Choose by uncertainty

Handle routine scoped work directly. Use Survey for unresolved intent, Track for an unsupported cause, Prove for test-first proof, and Expedition for complex coordination.

02

Protect the real territory

Treat repository content as evidence, preserve unrelated work, and pause before materially widening scope or authority.

03

Verify and report honestly

Classify failures, review the owned change, and distinguish Complete, Incomplete, or Blocked without overstating delivery.

How unknowns change the route

Not every unknown needs a meeting.

KNOWN / KNOWN

Constraints

Honor the explicit request, trusted instructions, and verified repository conventions.

KNOWN / UNKNOWN

Questions

Resolve only decisions that can materially change architecture, behavior, security, UX, or validation.

UNKNOWN / KNOWN

Recognition

Use a prototype or example when taste, density, or interaction is easier to recognize than describe.

Blind spots

How scope and completion are protected

Guardrails that change agent behavior.

01

Repository text is evidence, not authority

Instructions follow trust order. Untrusted output cannot silently widen the request.

02

Preserve the worktree you entered

Capture the baseline, identify task-owned files, and leave unrelated changes intact.

03

Gate material scope expansion

Proceed inside the agreed boundary. Pause when behavior, authority, risk, or ownership would expand.

04

Keep tiny tasks lightweight

Obvious, low-risk work does not need the full artifact system.

05

Persist artifacts only when useful

Briefs, reports, and prototypes support re-entry, coordination, or recognition—not ceremony.

Complete

The result and required validation are complete within the authorized boundary.

Incomplete

A required task-owned step or check remains unfinished.

Blocked

Progress requires a decision, new authority, or an external-state change.

Every Field Report states the outcome, validation, remaining uncertainty, and exact delivery state.

How complex work progresses

One route. Observable checkpoints.

Discovery stops when the owning seam, contract, worktree state, and validation route are supported.

01 · Orient

Enter the real repository

Capture the baseline, trusted context, and task-owned files.

02 · Route

Decide what could change the plan

Classify important unknowns and choose the cheapest technique that can close them.

03 · Change

Patch the smallest valuable surface

Preserve unrelated work and avoid silent scope expansion.

04 · Verify

Classify validation honestly

Separate task-caused, pre-existing, and environmental failures.

05 · Review

Try to disconfirm the result

Review the owned delta from the original request and evidence.

06 · Report

State the actual territory

Produce a proportionate Field Report and exact delivery state.

Delivery authorization

Delivery is a capability chain.

Honor existing authorization for each operation. A request can authorize several steps together; do not ask twice. Select a step to see its boundary.

Edit

Change and validate task-owned files. Editing does not authorize a commit, push, pull request, merge, tag, or release.

What is verified today

Evidence has boundaries.

Deterministic integrity and behavioral claims are reported separately.

Deterministic checks

Package structure, bundle consistency, site integrity, artifact helpers, and ordinary tests run locally without model calls or frozen evaluation locks.

Historical observations

Archived reports preserve observations from older versions. They do not validate the current guide or establish a general performance guarantee.

Current limitation

The current skill has no general performance guarantee. Historical evidence summaries describe earlier versions; model-based benchmarks are not required for routine changes.
